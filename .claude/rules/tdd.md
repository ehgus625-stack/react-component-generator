# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그쪽이 우선**한다. 이 파일은 기본값(fallback)이다.

## 1. 적용 기준

### 반드시 TDD 적용

- 비즈니스 로직
- API (핸들러, 엔드포인트, 응답 처리)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트 먼저)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **적용**한다.

## 2. RED-GREEN-REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 마라.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행 없이 실패를 가정하지 마라.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니다. 고친 뒤 다시 실행한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능은 넣지 마라.
- **신규 + 기존 테스트 모두 통과**하는지 전체를 실행해 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green 유지**: 변경마다 테스트를 실행한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 RED부터 시작한다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트 전에 프로덕션 코드를 먼저 작성했다면 **삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억에 의존한 재작성 모두 포함한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 끝난다. 단순하다고 판단한 코드가 가장 자주 깨진다. |
| "나중에 테스트 추가하겠다" | 나중은 오지 않는다. 사후 작성 테스트는 구현을 따라 쓰게 되어 버그를 잡지 못한다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. TDD가 더 빠르다. |
| "삭제하면 낭비다" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 삭제 비용도 없다. |
